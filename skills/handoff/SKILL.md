# Workflow handoff

Forward the caller’s `execution` fields unchanged on a single handoff. Use the default transport for native controls. `addDirs` accepts up to eight existing absolute directories in Claude, Codex, Cursor, and Gemini. Confirm external write scope before setting `metadata.harnest.writeApproved`. Codex requires write policy for `addDirs`.

Use prompt-only handoffs for attachments and forks. `attachments` accepts up to four absolute paths, each up to 256 KiB. Codex and Pi accept images. OpenCode and capable ACP agents also accept files. `instructions` appends up to 8,000 UTF-8 bytes in Claude and Pi. `sessionAction: "fork"` needs a `sessionId` and native support in Claude, Codex, OpenCode, or Pi. `maxTurns` is a positive integer for Claude print mode.

For a long-running single handoff on a host with visible background tasks, use the lead-owned [single-job observer](references/workflow-observer.md#single-job-observation). Launch through MCP once, then let the observer process wait. Restricted bridge workers cannot launch a shell monitor; use them for bounded work that fits their turn budget. Do not increase that budget to simulate a persistent observer.

For a multi-agent graph with dependencies, mixed harnesses, or retry from a failed step, read [agent graphs](references/agent-graphs.md) before constructing requests. For task-shaped harnesses — fan-out and synthesis, adversarial verification, per-item implement/verify/fix pipelines, tournaments, quarantine triage, and batching past 256 nodes — read [dynamic workflows](references/dynamic-workflows.md) before designing the graph. `handoff_graph_*` coordinates the graph; each node remains a complete handoff. The single-handoff instructions below apply to individual nodes, not to the entire mixed-harness graph.

A handoff is a subagent spawn with hop tax: new process, re-stated brief, cold cache, tokens on another meter. Use it where that tax buys something.

Hand off when the work is **big, independent, or long**: huge research (multi-source context that would flood this session), self-contained briefs needing no session state, long runs whose transcript must stay out of the lead context, burning down fresh limits elsewhere, second opinions on contested questions.

Do NOT hand off when the hop costs more than the work: quick questions, single file reads, small edits, anything needing this session's accumulated context or repo state, taste-critical work with no review loop across the hop, multi-turn debugging (every turn re-states context). Your session cache is the most valuable context you have — keep context-dependent work in-session, native subagent at most.

Use the model the user names in `route.model` and any effort they name in `route.thinking`. If the user names an exact model ID, set `metadata.routing.modelVersion` to `pin` to keep that version. Leave native aliases such as `sonnet` or `opus` unpinned, because pin mode rejects aliases. If the user leaves the model out of the prompt, use their saved routing preferences. If neither supplies a model, omit `route.model` so the downstream CLI can use its configured default.

Use `handoff_workflow` for one downstream workflow. Pi never runs Claude models (rejected as policy) — Claude models run only via `target: "claude"` (Claude Code CLI). Use `handoff_compare` when the user requests multi-model testing, independent opinions, or parallel research on the same question. Call `handoff_host_info` first when unsure which launch path the current host expects.

For comparison, build one read-only request and 2-16 named candidates. The tool sends the identical task, context, workflow, policy, and completion contract to every lane after resolving each candidate independently. Verify the returned resolved routes are distinct, retain every lane receipt, and compare agreements, disagreements, evidence quality, usage, and failures. Keep each opinion attributable; consensus is supported only where the receipts independently agree. Shared-checkout writes are rejected—implementation bake-offs require one isolated worktree per writer.

1. Build one request containing the exact task, absolute cwd, context capsule, optional workflow (Taskflow compatibility only for explicit workflow.spec/workflow.nodes), route if needed, write policy, and limits. Name a target (or use `auto` on a graph node) and follow the model choices above. A bare OpenCode target depends on a configured OpenCode lane or trusted resolver to fill its model. Pi may omit route for profile defaults. Cursor accepts an optional `route.model` passed verbatim as `cursor-agent --model` (discover with `cursor-agent --list-models`). Claude accepts an optional `route.model` alias or full ID (`sonnet`, `opus`, `claude-opus-5`) passed verbatim as `claude --model`. Verify the actual model from `modelUsage` afterwards. `route.thinking` maps to `claude --effort` (`low`, `medium`, `high`, `xhigh`, `max`; `off`/`minimal` are dropped because Claude has no equivalent). Cursor print defaults to `--mode ask` for read-only and `--force` for approved write. `policy.mode: "plan"` selects read-only planning and `policy.sandbox: true` enables the native shell sandbox. Both omit `--force`. Cursor rejects granular tools, cost budgets, and `sandbox: false`. Claude print mode supports both read-only (`--permission-mode plan`) and write (`acceptEdits`), supports `maxCostUsd` via `--max-budget-usd` (client-side estimate), and accepts `policy.tools.allow` for `Read`, `Glob`, and `Grep` and `policy.tools.deny` for exact native names. Claude session transport rejects tool lists. Plain Pi handoffs and fresh local OpenCode 1.18.18 prompt handoffs support exact built-in `policy.tools.deny` lists, with no Taskflow. Codex accepts an optional `route.model` passed verbatim as `codex exec -m`; read-only maps to `--sandbox read-only`, write to `workspace-write`, and granular `tools`/`maxCostUsd` are rejected. Gemini and Amp are prompt-only attached one-shot targets. Gemini requires exactly v0.62.0 and no OS system-policy TOML; read-only excludes shell/write, while write mode adds the verified coding tools including `run_shell_command` for build/test, `write_file`, and `replace`. `policy.tools.allow` and `policy.tools.deny` narrow Gemini's native tool policy. Its process cwd is not a filesystem sandbox because inherited include directories cannot be cleared. Amp accepts only explicit write policy with approval, empty tools, null `maxCostUsd`, and `route.variant` set to `low`, `medium`, `high`, or `ultra`; generated settings reduce risk but are not containment. Both reject `execution.transport: "session"` and live controls; follow-ups use `execution.sessionId`. Amp supports native Linux/macOS, or the entire MCP server running inside WSL; native Windows rejects before inference. DeepSeek models run via Pi or OpenCode provider routes — there is no DSH downstream target. For an ordinary text leaf, set `context.requiredResultFields` to `finalText` only and put exact acceptance canaries in `context.requiredText` (they match only as standalone result lines — the token alone or `RESULT: TOKEN`; Claude Code nodes need real task text and a final `RESULT: <canary>` line because bare echo prompts read as prompt injection). Add `evidence`, `tests`, or `risks` to `requiredResultFields` only when the selected adapter is explicitly configured to populate those receipt arrays; prose labels in the model's final text do not populate them. Outer receipt metadata such as `route`, `sessionId`, and `usage` is validated after completion and must not be listed as a required result field. When the user asks policy to choose, put bounded declarative intent in `metadata.routing`: `mode: auto` lets policy select, `mode: prefer` gives the explicit route a strong score bonus, and absent mode keeps an explicit provider/model pinned. A one-word `tier` (`quick`, `balanced`, `deep`, `review`) sets speed/quality intent without naming models; `difficulty` (`trivial`, `bounded`, `hard`) describes the work so cheap lanes hold trivial tasks and hard tasks earn flagships; `harnessOrder` ranks harness preference. Effort derives too: tier/difficulty imply a thinking level (capped at `high`) unless `route.thinking` names one. See `docs/preferences.md` for the full precedence (explicit flag > worker pin > project > user > callee default) and ordering rules (weights, prefer/avoid, priority, require). Session selection comes from `execution.sessionId` (Cursor/Claude/Gemini/Amp/generic ACP resume, OpenCode/Pi session continue); never put resolver paths or executable code in request metadata. Always set `policy.write` explicitly; never rely on a host's Plan Mode as a permission boundary. Completion: every acceptance criterion, routing intent, and permission boundary is represented once. Detail: `references/routing-precedence.md`, `references/live-trace-loop.md`.
   On guarded hosts, every write-capable form (`policy.write:true`, `policy.readOnly:false`, or `policy.allowWrites:true`) requires the exact marker `metadata.harnest.writeApproved:true` after the lead confirms the intended scope; there is no separate `writeScope` protocol field. A nested handoff remains subject to the child host's approval and sandbox restrictions and cannot widen them. If an authorized write is blocked, do not delegate another handoff to bypass the denial: return the complete draft in completion JSON using `finalText` plus `artifacts`/`files` so the lead can save it. `finalText` is bounded to 64k characters and each artifact entry to 4k; return a patch or chunk larger drafts.
2. Give every request an explicit request ID and default to background execution. Bridge workers are thin forwarders, not orchestrators: one `handoff_workflow` call, then poll, then return the receipt verbatim. Never read the repo, poll other jobs, summarize, or paraphrase machine fields inside the bridge; that context dies with the bridge and the downstream harness re-reads anyway. Launch the handoff through the current host's native child-agent surface so the operator keeps transcript visibility: on Claude, invoke the native `workflow-rescue` subagent (or `harnest:opencode-worker` / `harnest:pi-worker` / `harnest:cursor-worker` / `harnest:claude-worker` / `harnest:codex-worker` / `harnest:gemini-worker` / `harnest:amp-worker` / `harnest:acp-worker`) via the Agent tool so the receipt returns through the subagent transcript; inside that subagent, call `handoff_workflow` once. On Codex, call `handoff_workflow` directly as an MCP tool, or spawn the matching `opencode_worker` / `pi_worker` / `cursor_worker` / `claude_worker` / `gemini_worker` / `amp_worker` / `acp_worker` native child thread when panel visibility is required. On OpenCode, call `handoff_workflow` directly as an MCP tool (tool names are prefixed `harnest_`), or launch the task tool with the matching `opencode-worker` / `pi-worker` / `cursor-worker` / `claude-worker` / `codex-worker` / `gemini-worker` / `amp-worker` / `acp-worker` subagent for a visible child session. On Pi, call `handoff_workflow` directly through the harnest extension; Pi has no child-agent surface, so bounded `handoff_status`/`handoff_trace` pages are the operator view. On Cursor, call `handoff_workflow` directly as an MCP tool (`/handoff` runs the skill, `@handoff` attaches it as context); Cursor automations do not inherit UI MCP servers in subagents, so prefer direct calls, or run one `cursor-worker` background agent per handoff for visibility. Everywhere, `handoff_host_info` reports the exact launch path for the current host. Completion: the queued receipt returns a job ID and matching context digest before downstream model work begins.
3. Retain both identifiers. Use `handoff_sessions` to rediscover durable jobs, `handoff_fleet` to watch every running agent at once (progress, recent messages, per-agent steer mode), `handoff_status` for compact state, and `handoff_trace` for bounded event pages. For live tracking, retain `nextSequence` and pass it as `afterSequence` so only new events enter the parent context; poll every 1-2s. The native child transcript is the canonical live view where one exists (Claude/Codex/OpenCode worker thread); `handoff_trace` is the durable pollable mirror for hosts without one (Pi, Cursor IDE) and for recovery after the lead context dies. Structured native deltas arrive as trace events, so trace polling is live streaming for one-shot targets. See `docs/live-transcript.md`. Every parent update must name `trace.progress.phase`, `current`, recent milestones, and `lastMeaningfulAt`; a fresh worker heartbeat without new meaningful progress is content-stalled, not proof that work is advancing. When the parent supplies new guidance during a run, call `handoff_message` with a new command ID; use `steer` for the next agent step and `follow_up` for the next turn. When the provider/model should change, call `handoff_reroute`; the change applies to the next model request. Treat only `applied` as acknowledged, surface `uncertain`, and never reuse a command ID for different content. The wall-clock timeout is absolute and is never extended by heartbeat traffic. If the initial MCP response is lost, recover status using the request ID. Use `handoff_cancel` or `handoff_resume` only for that job. Automatically resume at most once and only when the request is read-only; write-capable retries require the lead to review the trace and approve. Cursor, Claude, Codex, Gemini, Amp, and generic ACP follow-ups resume with `execution.sessionId` set to the receipt's native session ID. These one-shot modes reject live `handoff_message`/`handoff_reroute` as `unsupported-control`; Gemini, Amp, and generic ACP also reject `execution.transport: "session"`. Completion: the receipt state is terminal, then retrieve `handoff_result`.
4. Accept the handoff only when the receipt contains the matching request ID and context digest, final text, resolved route, session/workflow identity, usage, and the receipt's evidence, tests, and risks arrays. Those arrays may be empty for a simple read-only leaf unless the request explicitly required them to be populated. Treat missing fields, transport errors, and partial runs as incomplete.

Keep lead authentication native. Downstream OpenCode/Pi/Cursor/Claude/Codex/Gemini/Amp providers and registered ACP agents use their own supported credentials. The premium lead reviews and integrates; the downstream workflow never merges or deploys unless the request explicitly grants that authority.

## Native route controls

For Codex one-shot handoffs, forward an explicit `route.profile` for `--profile` and `route.serviceTier` for native `service_tier`. Claude one-shot accepts a named `route.agent` via `--agent` and `route.serviceTier: "fast"` via the native fast setting. In JavaScript workflows, select one-shot transport explicitly when using these controls.

## Generic ACP

Use `target: "acp"` only with an explicit `route.agent` that names a trusted machine-local `acp.agents` registration. Never accept the executable, arguments, modules, or environment secrets from request content, prompts, or registry metadata. The operator installs and authenticates the native agent separately. `trusted: true` is consent for that executable to load its native configuration; it is not a read-only guarantee or sandbox, and native hooks, plugins, or MCP servers can run before initialization.

Generic ACP is write-only: require `policy.write: true` and `metadata.harnest.writeApproved: true`. Reject unsupported route and policy controls before launch. Fail explicitly when unsupported negotiated capabilities or client callbacks are discovered or requested. Follow-ups reuse the observed `execution.sessionId`; never silently start a fresh session. The registration may declare ACP protocol major 1 or 2; registry package version never determines protocol major. Standard bounded filesystem/terminal client services are v1-only. Unknown permissions reject and the client never chooses a persistent allow or approval bypass.

Forward explicit `route.model`, `route.variant`, and `route.options` only as native ACP IDs and values. The session must advertise each choice before Harnest sends the prompt. Options accept at most 16 entries with string or boolean values.

Use the single generic `harnest:acp-worker`, `acp_worker`, or `acp-worker` bridge for Claude, Codex, or OpenCode visibility. Do not create per-registry-agent workers. Direct MCP callers need no bridge, Forge, or T3.

## Fan-out

The lead owns fan-out. When the user asks for parallel research, launch at most six bridge workers at once and queue the rest. Each bridge owns one handoff and never spawns workers. Each lane gets its own request ID (`<base>:<lane>`) and durable receipt. Keep lanes attributable; compare agreements, disagreements, evidence quality, usage, and failures without blending consensus. For implementation bake-offs, `handoff_compare` fans one identical read-only request to 2-16 routes; parallel writers require one isolated worktree per writer because shared-checkout writes are rejected.

## Subagents talking to subagents

Any worker can steer any running handoff it can name — including another worker's. The pattern: `handoff_sessions` (or a shared job ID) to discover it, `handoff_message` with a fresh `commandId` to speak, `handoff_trace` with `afterSequence` to read the reply. Rules: one `commandId` per message, never reuse an ID for different content; `delivery: steer` lands at the next agent step, `follow_up` at the next turn; only `applied` counts as acknowledged (`uncertain` means reconcile from the trace, then resend with a new ID if needed). One-shot targets (Cursor, Claude, Codex, Gemini, Amp, and generic ACP) cannot be steered mid-run — address them by resuming with `execution.sessionId`, or leave findings in the trace for the parent to carry. Review lanes message each other through the shared board (`"to": [{"lane", "message"}]`) instead — same idea, structured per round.

## Multi-model review loop

`handoff_review` runs 2-8 read-only reviewer lanes against one rubric with a shared findings board and lane-to-lane messages, then tallies scores. It loops opinion-convergence only — it never implements:

1. One call runs up to 3 rounds (default 2). Round 1 scores independently; rounds 2+ share every lane's findings and scores, route directed `@lane` messages, and re-score.
2. Each lane must end with the fenced JSON score block covering every rubric factor, or it abstains. Fewer than 2 voting lanes fails the review.
3. `completed` = average reached threshold (default 9/10). `partial` = rounds exhausted below it, with consolidated deduplicated findings to implement.
4. Apply the findings yourself (or hand them to a worker), then re-invoke with `previous: { summary, scores }` — the next loop confirms what was fixed and scores the current state only.

Review lanes are read-only by construction (write policy is rejected like `handoff_compare`), capped at one fallback-free run each, and resolve to distinct routes so the same model twice is rejected. Follow the user's model and effort choices for each lane.

## File-edit ladder

Pick the narrowest rung that satisfies the task, per request, not per session:

1. Read-only review: `policy.write: false`. OpenCode denies edits; Pi restricts `allowedTools`; Cursor maps to `--mode ask`; Codex reviews use read-only sandbox; Gemini permits its safe read-tool allowlist. Amp and generic ACP reject read-only before spawn, so use another target. Use for pre-merge and adversarial passes.
2. Fix in place: `policy.write: true` with explicit parent authorization. OpenCode allows edits via `OPENCODE_CONFIG_CONTENT`; Cursor uses default mode with `--force`; Codex uses `workspace-write`; Gemini adds the verified coding tools, including `run_shell_command` for build/test, `write_file`, and `replace`; Amp requires empty tools, null `maxCostUsd`, native Linux/macOS or the entire MCP server inside WSL, and the write-approval marker; native Windows rejects before inference. Generic ACP requires an explicitly trusted `route.agent`, `policy.write: true`, and `metadata.harnest.writeApproved: true`.
3. Parallel writers: one isolated worktree (or Cursor `--worktree` / cloud branch) per writer, each with its own request ID. Never run parallel writers on a shared checkout.
4. Untrusted or cloud work: isolated VM/branch per run with hooks gating writes and network.

Granular `tools` lists and `maxCostUsd` budgets are enforced only where the harness adapter supports them. Unsupported fields are rejected before inference rather than silently weakened.

Raw downstream events are append-only local trace data and do not belong wholesale in the parent prompt. Use only the bounded/redacted `handoff_trace` page needed for the current decision. The receipt must carry the trace reference, event count, semantic progress snapshot, last activity, heartbeat, and recovery lookup key so tool/API failures cannot leave the lead with an unidentifiable run.
