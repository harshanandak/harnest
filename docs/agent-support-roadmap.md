# Agent support roadmap

Harnest MCP supports OpenCode, Pi, Cursor, Claude Code, Codex, Gemini CLI, attached Amp, and explicitly registered machine-local ACP agents as downstream targets. Gemini CLI and Amp can also act as direct MCP lead clients. Devin has a documented direct MCP lead-client setup and may be selected through the generic, write-only ACP route; native live verification, isolated/read-only startup, and cloud execution remain pending. Kimi, Qwen and GitHub Copilot are deferred by user choice. An agent's ability to connect to an MCP server does not establish that Harnest can execute and recover that agent's work.

This assessment was prepared on 2026-10-03 from official documentation, source, and model-free adapter/registration fixtures. It is not an authenticated live integration test. No model calls, cloud sessions or paid inference were performed.

## Gemini CLI: prompt-only attached support

Gemini documents [headless JSONL output](https://geminicli.com/docs/cli/headless/) and [ACP over stdio](https://geminicli.com/docs/cli/acp-mode/). Headless events include session/model initialization, assistant/tool events, errors and a terminal result. Harnest's initial adapter uses the prompt-only attached path in the request cwd, preserves the stable-context-first envelope, requires a successful terminal result and nonempty final answer, and retains bounded progress/usage.

Read-only policy requires exactly Gemini CLI v0.62.0 and uses temporary settings/admin policy because the [configuration reference](https://github.com/google-gemini/gemini-cli/blob/main/docs/reference/configuration.md) and source show that plan mode alone cannot satisfy Harnest's policy contract. Preflight refuses any OS system-policy TOML that the launch cannot override. The generated read-only policy uses a fixed safe read-tool allowlist and excludes shell and writes. Write policy adds the verified standard coding tools, including `run_shell_command` for build/test, `write_file`, and `replace`. Unknown tools, plan exit, MCP, extensions and hooks remain denied. The adapter never uses approval-bypass modes. The cwd is the process directory, but inherited `includeDirectories` cannot be cleared, so this policy is not a filesystem sandbox or read boundary. Unsupported policy, route, workflow, live-control and session-transport requests fail before inference.

The published v0.62.0 source establishes a concrete blocker:

- [Plan policy](https://github.com/google-gemini/gemini-cli/blob/v0.62.0/packages/core/src/policy/policies/plan.toml#L53-L81) allows `exit_plan_mode` in noninteractive execution. [The tool implementation](https://github.com/google-gemini/gemini-cli/blob/v0.62.0/packages/core/src/tools/exit-plan-mode.ts#L207-L268) switches an allowed noninteractive exit to YOLO approval. Plan policy also allows certain plan-file writes.
- [ACP tool execution](https://github.com/google-gemini/gemini-cli/blob/v0.62.0/packages/cli/src/acp/acpSession.ts#L702-L801) calls the client's permission handler only when native confirmation is required. An upstream ALLOW can therefore execute without the client getting a permission request. Rejecting every ACP permission request is insufficient containment.
- [Policy configuration](https://github.com/google-gemini/gemini-cli/blob/v0.62.0/packages/core/src/policy/config.ts) gives user/extension/admin policy higher precedence than default rules and synthesizes ALLOW rules from native tool/MCP settings. An invocation-level supplemental policy is not established as replacing all machine policy.

The isolated launch and fake-process fixtures cover Harnest's policy preparation, launch/receipt contract, structured terminal result, resume, cancellation, timeout, output bounds and rejected unsupported cases without spending tokens. A disposable authenticated live run remains required before claiming live enforcement against a current installed Gemini CLI.

Gemini ACP remains outside the initial transport contract. `execution.transport: "session"` and mid-run message/reroute controls fail closed. Documented native continuation is exposed only as a later prompt-only handoff with `execution.sessionId`. Native model/usage behavior and cancellation acknowledgement are preserved from observed structured events; live validation is still pending.

## Amp: attached prompt-only support

The [TypeScript SDK](https://ampcode.com/docs/sdk/typescript) wraps the CLI and returns a stream of initialization, assistant/tool and terminal success/error events. It supports continuation, AbortSignal and terminal session identity, final output, usage and permission denials. The [execute-mode guide](https://ampcode.com/docs/cli/execute-mode) distinguishes attached local execution from detached orbs. The [external API](https://ampcode.com/api/external) directs agent automation to CLI/SDK.

The initial adapter uses attached execution for explicit write-capable requests only. [Tools](https://ampcode.com/docs/tools) run without approval by default; custom settings are lower precedence than workspace settings, and execute mode can load local plugins without a documented plugin-disable flag. Harnest therefore rejects read-only before spawn. It requires `policy.write: true`, the write-approval marker, empty tools and null `maxCostUsd`. Generated restrictive settings are risk reduction, not containment. The adapter persists Harnest request/digest-to-thread mapping because native thread identity does not carry that contract. Detached orbs, live controls and session transport fail closed.

[Native authentication](https://ampcode.com/docs/cli/execute-mode) uses saved Amp login state or an operator-provisioned `AMP_API_KEY` user access token for automation; Harnest lets Amp resolve it without reading, forwarding or logging its value. A non-human service-user inference credential was not established by the reviewed docs. Execution consumes the operator's Amp account usage/credits; determine the applicable account plan and approval before any paid run. The [acceptable-use policy](https://ampcode.com/terms/aup) constrains automated usage and rules out treating free usage as a generic inference backend. No current price or cost estimate is asserted here.

The [CLI guide](https://ampcode.com/docs/cli) documents native macOS and Linux, and Windows through WSL. Amp-target execution therefore supports native Linux/macOS or the entire Harnest MCP server running inside WSL; native Windows rejects before spawn. [Runners](https://ampcode.com/docs/cli/runners) execute with the starting user's file and credential access. Local execution does not establish offline storage or private thread visibility. `route.variant` is limited to `low`, `medium`, `high`, or `ultra`; arbitrary provider, model and thinking fields reject before inference. This is source support, not a claim of a live native macOS run.

Detached orbs remain outside the initial scope: the reviewed docs do not establish controller-restart recovery and post-detach cancellation of the active turn. That is an unresolved documentation gap, not proof that the product lacks those features. Model-free fixtures cover initialization identity, ordered stream, denied permission, continuation, terminal result, abort, output bounds and failure classification. An authenticated live run remains unverified.

## Generic ACP: explicit local registration

The generic ACP target launches only a machine-local command stored under `acp.agents` and selected by `route.agent`. Registry metadata and requests cannot supply executable code. The operator installs and authenticates the agent natively, supplies its command/arguments, chooses ACP protocol major when known, and records `trusted: true`. That trust flag is consent to native configuration imports; it is not a read-only or sandbox guarantee.

The contract is intentionally write-only and requires explicit normalized write approval before spawn. It preserves native session identity, negotiates supported ACP v1/v2, streams bounded updates, and supports terminal prompt handling and cancellation. Unsupported route and policy controls reject before launch; unsupported negotiated capabilities or client callbacks fail explicitly when discovered or requested. Standard bounded filesystem/terminal client services are v1-only; arbitrary callbacks are not advertised. Registry package version is provenance and never determines ACP protocol major. `doctor` enumerates metadata only and performs no native initialization, login, help, or version probe. Model-free fake-process tests establish the client contract; no registry agent is claimed live-verified by this documentation.

## Devin CLI: MCP client setup, generic ACP execution unverified

The official [local Devin CLI](https://docs.devin.ai/cli) is distinct from Devin Cloud and supports stdio MCP client configuration. See [the Harnest client setup](devin-cli.md). The earlier cloud-only classification was incomplete.

An earlier model-free startup probe reproduced imports of existing MCP configuration and connection attempts despite redirected home/profile settings. Safe startup isolation of imported/native MCP, plugins and hooks remains unproven. Devin may be registered explicitly through the generic ACP write path, but Harnest does not provide a dedicated Devin target or per-agent worker and does not claim a successful native Devin handoff. The next acceptance step is an operator-authorized disposable live run, followed by separate proof of pre-start isolation and read-only enforceability while preserving native authentication.

## Devin Cloud: separate integration

Devin offers an [official remote MCP server](https://docs.devin.ai/work-with-devin/devin-mcp) and [v3 Sessions REST API](https://docs.devin.ai/api-reference/v3/overview). REST is the recommended candidate boundary because session identity, messages and termination are explicit durable objects. The [authentication guide](https://docs.devin.ai/api-reference/authentication) recommends non-human service users with RBAC for automation.

The [create operation](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions) and [get operation](https://docs.devin.ai/api-reference/v3/sessions/get-organizations-session) expose identity and lifecycle metadata. [Messages](https://docs.devin.ai/api-reference/v3/sessions/get-organizations-session-messages) support paginated recovery; [sending a message](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions-messages) can resume work. [Termination](https://docs.devin.ai/api-reference/v3/sessions/delete-organizations-sessions) is a distinct operation. These are documentation claims; cancellation races and acknowledgement still require tests.

Before execution, require an explicit organization-scoped service-user configuration, ACU limit and mandatory [security profile](https://docs.devin.ai/product-guides/security-profiles). Persist the returned session identity immediately and poll/checkpoint state and message cursors. Assemble the terminal receipt from verified terminal status, structured output and final message; do not invent a canonical final-text event. Create idempotency and duplicate-create recovery need explicit tests.

Devin execution consumes the organization's ACU usage budget. An ACU cap bounds that unit of consumption; it is not a dollar-cost guarantee. Confirm the operator's plan, applicable rates and paid-run authorization before any create call. This assessment does not assert a current price or authorize a billed session.

Cloud execution changes the data boundary. The [handoff guide](https://docs.devin.ai/work-with-devin/devin-handoff) transfers repository/branch, context and potentially uncommitted changes. This requires explicit user authorization when introduced. Preserve waiting-for-approval as a nonterminal state with a human-action URL; no reviewed API operation conclusively approves or denies each pending action. Streamable HTTP is transport, not proof of a resumable event stream.

Required acceptance sequence: create, persist identity, progress, approval wait, resume, terminal receipt, terminate, controller-restart recovery and duplicate-create protection. Devin Cloud remains unsupported by this release.

## Release boundaries

Gemini and attached Amp use their native execution models. Generic ACP adds one explicit local-registration route and one generic bridge worker across hosts; it does not create per-agent integrations or imply that every registry entry is verified. Devin can connect as a documented MCP lead client and may use the generic write path, while native live proof, safe startup isolation, read-only execution, and cloud execution remain separate pending work. Kimi, Qwen and GitHub Copilot remain deferred. Adding a dedicated integration still requires the same complete registration and meaningful adapter-test bar.

Review the inherited dependency advisories before public distribution. Resolve the intermittent same-length trace-cache invalidation failure observed in the full baseline suite; passing focused reruns do not fix it. Source changes, fake tests, successful host installation and live agent execution are distinct evidence. See [public installation](public-installation.md) for publication readiness. Forge remains internal maintainer tooling and is not a user dependency.
