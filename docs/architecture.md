# Architecture

## Shared daemon

Claude Code and OpenCode connect directly to the per-user daemon at `http://127.0.0.1:41237/mcp`. Pi calls the same endpoint through its extension. Codex, Cursor, Gemini CLI, Amp, and the [ACP preset lead hosts](users/integrations.md#acp-presets-as-lead-clients) use the stdio bridge. The daemon builds one JobStore, Companion and session pool, GraphRunner, routing settings service, workflow registry, and lazy dynamic facade after it wins the loopback bind. Each stateless MCP exchange creates its own protocol object over those services. Legacy initialize and modern discovery expose the same catalog. Connection loss leaves accepted work running. Reattach using the existing job or request identity.

Startup comes from a [host installer](users/integrations.md), host hook or extension, stdio bridge, or `bun run daemon start`. Run the host installer with the intended state settings and `PATH`. It registers a login item by default using Windows Task Scheduler, a macOS LaunchAgent, or a systemd user unit. The item captures the resolved job and daemon directories, `PATH`, and an explicit allowlist of non-secret Harnest runtime settings. Use `--no-autostart` for on-demand startup only.

Use `bun run daemon stop` for a graceful stop. If it reports `busy`, wait for active work to finish before stopping. Run `bun run daemon uninstall-autostart` as the installing user to remove the login item while keeping durable jobs and host configurations. On Linux, use the same `XDG_CONFIG_HOME` as at install. A newer client requests replacement only when the daemon has no active in-process work. Detached job and dynamic workers retain their independent ownership.

The listener checks Host, Origin when supplied, and the local bearer before decoding MCP requests, with a 2 MiB request cap. A private `token` file next to non-secret `daemon.json` discovery stores the credential. On Windows the directory is under `%LOCALAPPDATA%/harnest/daemon/`, on macOS it is `~/Library/Application Support/harnest/daemon/`, and on Linux it is under `$XDG_STATE_HOME/harnest/daemon/` (default `~/.local/state/harnest/daemon/`). At startup, the launcher verifies the listener before sending the bearer. Same-user code can read the token and user-level MCP headers. Downstream processes inherit the daemon's ordinary native authentication environment with Harnest token variables stripped.

The stdio bridge forwards JSON-RPC to the same daemon. On exchange failure it ensures the daemon is running and retries discovery or requests whose connection was refused before delivery. If a tool call may have reached the daemon, recover by job or request ID. Explicit standalone stdio uses `src/mcp-server.mjs` and owns a separate services container.

Routing customization uses a shared `RoutingSettings` service exposed through MCP and Pi's native extension. It reads the existing user policy, expands optional named presets into the current deterministic selector, and writes through the same locked atomic policy writer used by the setup/pressure commands. Revision checks occur inside that writer lock. Preview calls the actual route resolver with a captured policy snapshot and never creates a handoff. Running jobs retain their previously resolved requests. Advanced policies and trusted executable resolvers remain in the selection path and appear in preview provenance.

Claude Code, Codex, OpenCode, Cursor, Gemini CLI, and Amp consume the same MCP routing tools; Pi registers the same definitions through its native extension. Both paths use the canonical user file and shared writer lock, so edits from one host appear on the next routing decision in another. Daemon clients share the daemon?s configured policy path and startup settings. Legacy standalone instances can select their own path. No routing feature depends on OpenCode's plugin APIs. Preview reports its snapshot revision and independent runtime-state boundary; executable-hook/config hot replacement is outside this implementation.

`latest` and `pin` version selection runs in the shared resolver. Standard adapters use bounded, cached native metadata discovery. Custom adapters own their catalog and can supply `routing.modelCatalog`; without it, freshness is unverified and no native CLI is queried on their behalf. MCP/Pi previews reuse the same catalog controller as execution, while resolver circuit-breaker state remains independent.

```text
Claude Agent wrapper ─┐
                      ├─ Harnest MCP ─> OpenCode adapter ─> OpenCode native (optional Taskflow for explicit specs)
Codex skill + MCP ────┤                  ├─> Pi adapter ───────> Pi native (optional Taskflow for explicit specs)
Cursor MCP ───────────┘                  ├─> Cursor adapter ───> cursor-agent print (stream-json)
                                         ├─> Claude adapter ───> claude print (stream-json)
                                         ├─> Codex adapter ────> codex exec (JSONL + last-message file)
                                         ├─> Gemini adapter ───> Gemini headless structured stream
                                         ├─> Amp adapter ──────> Amp attached structured stream (Linux/macOS/WSL)
                                         └─> ACP adapter ──────> registered ACP agent (attached write-only)
                                         <─ terminal receipt ──
```

## Boundary

JavaScript workflows use a separate durable runner, journal and detached worker. QuickJS owns script control flow and exposes bounded JSON callbacks only; Harnest owns every child handoff. Saved definitions retain content-addressed source revisions. See [JavaScript workflows](javascript-workflows.md) for the ordered-prefix replay contract.

Dynamic-store mutations are queued per run and committed in batches of at most 32 under the run and journal locks. Each runner mutation checks ownership against its current input record. Callers resolve only after journal append and atomic snapshot publication; a rejected callback cannot contaminate later mutations. Failed publication may leave diagnostic events ahead of the snapshot, so subsequent sequence allocation checks the durable journal tail. Control polling uses a compact cache validated by file identity, size and timestamps, without replacing the full run snapshot. Explicit terminal-history compression retains a verified journal prefix and supports restoration and subsequent replay.

The single-job CLI uses `JobObserver`, a passive reader of atomically published snapshots and bounded trace pages. It retries around writer locks and changed file identity/size/timestamps without creating or deleting locks. It never repairs request indexes; missing indexes require recovery through Harnest and reattachment by job ID. `JobStore` retains the existing locked read/write and recovery behavior for execution owners. An observer may lag a writer; its output does not replace a validated terminal receipt.

Explicit session transport uses Claude Agent SDK, Codex app-server or Cursor ACP. A Harnest-owned bounded pool reuses adapters only for an explicit native session ID with matching cwd, policy and route. Independent requests start independent conversations. Native session leases under the shared job store prevent two Harnest owners from resuming one conversation. Coordinator death alone never releases a lease: the native subprocess might still be alive, so orphaned ownership requires reconciliation. Idle eviction and worker shutdown close owned connections before releasing their leases. Cleanup failures preserve the original result/error and prevent unsafe retries. Delivered or queued controls without native acknowledgement remain uncertain in the parent receipt. Gemini and Amp start as prompt-only attached one-shot targets. Generic ACP is an attached write-only target selected by `route.agent`. All three reject `execution.transport: "session"` and live controls, while documented native continuation remains available through `execution.sessionId` on a later handoff.

Harnest also coordinates mixed-harness DAGs through `handoff_graph_*`. Each node is one prompt-only handoff with its own route and receipt. Graph state lives separately beneath the job store, and resume preserves completed nodes. The graph scheduler owns dependencies and concurrency; an individual harness still owns its node's execution. See `docs/agent-graphs.md` for the approved contract.

For an individual handoff, the lead chooses `opencode`, `pi`, `cursor`, `claude`, `codex`, `gemini`, `amp`, or `acp` once. The chosen harness or registered ACP agent owns its execution and trace. Pi/OpenCode execute a plain task natively and may run internal Taskflow phases only when an explicit FlowSpec is supplied and the optional package is installed; cross-harness dependencies belong to the graph coordinator. Cursor `cursor-agent --trust -p --output-format stream-json` is one-shot per invocation, uses `--workspace` as the working root, folds stream-json deltas into the trace while running, and resumes follow-ups with `execution.sessionId` (`--resume`). Codex `codex exec --json -o <last-message-file>` is likewise one-shot with `exec resume` follow-ups and `--sandbox` mapping; Claude `-p --output-format stream-json` resumes with `--resume` and enforces budgets with `--max-budget-usd`. Gemini requires exactly v0.62.0, uses temporary settings/admin policy, and refuses any OS system-policy TOML before inference; its read-only policy excludes shell/write, while write policy adds the verified coding tools including `run_shell_command` for build/test, `write_file`, and `replace`. Its process cwd is not a filesystem sandbox because inherited include directories cannot be cleared. Amp is write-only because native workspace settings/plugins prevent enforceable read-only containment; generated settings are risk reduction only. Both stream structured progress into the same trace and resume follow-ups from native session identity. Amp downstream execution supports native Linux/macOS or the entire MCP server running inside WSL; native Windows fails before spawn.

## Request path

`src/protocol.mjs` normalizes the request, resolves the working directory, and computes a canonical SHA-256 digest over the context capsule. `src/companion.mjs` creates a persisted job record, invokes one adapter, and writes state transitions through `src/job-store.mjs`. The MCP server exposes start, session listing, status, incremental trace, result, cancel, resume, message, and reroute. A control is persisted as `accepted` before delivery and becomes `applied`, `rejected`, or `uncertain` only after the adapter responds. Job snapshots are atomic; raw events append to a separate JSONL trace. Status folds those events into a bounded semantic progress snapshot containing the current phase, current activity, five recent milestones, and last meaningful timestamp. Trace reads are bounded, redacted, and sequence-addressable so a parent can poll only new events. A request-ID index recovers jobs whose first MCP response was lost, while worker heartbeats let a fresh process reconcile abandoned queued/running jobs to resumable `partial`. An outer wall-clock deadline terminates the receipt even if an adapter or Windows child process fails to settle; heartbeats never extend it.

## Background execution and foreground deadlines

Status separates meaningful downstream activity from worker liveness. Heartbeats, usage-only events, and empty Codex deltas do not reset `trace.progress.lastMeaningfulAt`. A running receipt reports `stalled` after five minutes without meaningful activity, alongside any active Codex tool's name, call identity, start time, and elapsed duration. The warning does not change the execution state or extend its deadline.

Cancellation first persists `cancellation.state=requested` and signals the owning adapter. Only adapter settlement acknowledges the stop; an adapter that does not settle within the acknowledgement window leaves a resumable `partial` receipt with `cancel-unacknowledged`. A queued job that has not acquired a lease can be cancelled immediately. Graph cancellation dispatches each attempt's stop once and measures its observation window after dispatch, so slow persistence cannot consume the child's acknowledgement window.

`handoff_workflow` background jobs are executed by a detached `node src/job-worker.mjs <stateDir> <jobId>` process: the server persists the queued job, spawns the worker detached (`detached: true`, ignored stdio, unref'd), and returns the queued receipt immediately. The worker claims the job's lease through the store's fenced claim and runs the same heartbeat, attempts, fallback, and terminal-receipt path as an in-process run, so the job survives the caller and the MCP server exiting. Graph children stay in-process because the graph runner owns and observes their lease. The worker honors `HARNEST_WORKER_ADAPTER=<module>` as a test seam that replaces real harnesses. A worker that throws outside that path records a failed receipt with `Companion#failQueued` before exiting 1, and a worker that dies before claiming leaves the job queued: `handoff_status` re-dispatches it after `queuedClaimTimeoutMs` (default 60s) up to `maxDispatchAttempts` (default 3) times, then settles it as a `partial` `unclaimed` receipt for the caller to resume or inspect.

The MCP boundary converts a foreground request whose declared `execution.timeoutMs` exceeds `FOREGROUND_SAFE_WAIT_MS` (55s, below the common 60s MCP client tool timeout) into a durable background job: the durable receipt carries `execution.foregroundConverted=true` with a bounded hint, and the caller polls `handoff_status`/`handoff_result` rather than waiting past its own tool timeout. Foreground requests within the safe wait still block for the terminal receipt; an omitted `timeoutMs` keeps the existing foreground wait, and `handoff_resume` keeps its foreground wait unless the caller passes `background: true`.

Once execution starts, all attempts share one monotonic deadline. Each adapter receives only the remaining `execution.timeoutMs`; fallback selection and persistence consume that same budget. An exhausted deadline prevents another adapter launch. The durable request retains the original budget so an explicitly resumed handoff gets its own execution window.

## Routing path

`src/routing-policy.mjs` evaluates declarative policy before an adapter is selected. Scope precedence is global, user, project, session, request; an explicit provider/model remains pinned unless request metadata opts into `auto` or `prefer`. Candidate rejection is capability-first (availability/circuit, target, write/read-only, Taskflow/live-control, context capacity, budget, deadline, avoid list), then surviving routes are scored on bounded quality/speed/efficiency/reliability axes with deterministic priority and lexical tie-breaking. The bounded explanation is copied to `receipt.routingDecision`; task/context text is never copied into it. After launch, a read-only run that fails with `transport`, `timeout`, `provider-auth`, `unavailable`, `downstream`, or `completion-contract` retries once on the next ranked route and records the switch with its `errorKind` in `receipt.routingFallbacks`; write-capable runs, cancellations, policy/validation rejections, and runs without a ranked alternative never fail over.

`src/routing.mjs` live-reloads the user JSON policy with a last-known-good fallback, then optionally calls the trusted machine-local resolver. Resolver import/call deadlines and an in-memory circuit breaker bound plugin stalls. The default resolver failure mode remains closed; operators may choose declarative passthrough. Request metadata is declarative only and cannot nominate a resolver module or executable code.

## Return path

Claude uses a native worker subagent, so the MCP receipt becomes an Agent-tool result in the parent context. Codex calls the same MCP tools through the bundled `handoff` skill or a native worker thread. Cursor calls the same MCP tools directly (prefer direct calls: Cursor automations do not inherit UI MCP servers in subagents) or via one `cursor-worker` background agent per handoff. Gemini CLI and Amp can also act as direct MCP lead clients through their native settings. All paths return the identical receipt schema. The native child transcript is the canonical live view where one exists; `handoff_trace` polling (`afterSequence=nextSequence` every 1-2s) is the durable mirror for direct clients and for recovery. See `docs/live-transcript.md`.

`completed` requires `result.finalText` plus every non-empty `context.requiredResultFields` value and every `context.requiredText` canary as a standalone result line (the canary alone or `RESULT: <canary>`). `failed` and `partial` require a structured error. `cancelled` is never rewritten as a failure or findings. The caller accepts a receipt only when its request ID and context digest match.

## Persistence and credentials

Routine status reads use a versioned semantic-summary checkpoint only when the journal's file identity, length and timestamps match. A mismatch replays the journal, including events appended before a snapshot write failed. Trace pages seek by sequence and read bounded byte windows rather than parsing the whole file for every poll. Sequence recovery checks file identity as well as size; an incomplete final line is separated before appending another event. Taskflow is imported only for an explicit `workflow.spec`/`workflow.nodes` request, so plain Pi/OpenCode handoffs and every other harness never pay that startup cost or require the optional packages.

Jobs default to the platform-local state directory and can be redirected with `HARNEST_STATE_DIR`. Requests and append-only traces contain task context and tool output, so the state directory must remain local and access-controlled. Harnest passes provider/model names but never reads, stores, or returns provider secrets; OpenCode, Pi, Cursor, Claude, Codex, Gemini, Amp, and registered ACP agents resolve credentials through their own supported configuration.

## Memory

Each job store retains up to 512 trace checkpoints and 8 MiB of accounted data, measured as the UTF-8 bytes of the job IDs and serialized checkpoints. The least recently used checkpoints leave first. Publishing a terminal snapshot releases its checkpoint. Recovery uses a 64 KiB read chunk and buffers at most 4 MiB per JSONL record. The trace summary counts malformed records and reports the last safe sequence. An oversized record stops recovery with a diagnostic.

CI caps peak RSS at 120 MiB per stdio server on Ubuntu and Windows. The direct and Claude plugin launches each run legacy initialization and modern discovery against the full tool catalog, then must exit cleanly after stdin EOF. The measurement includes the server and its telemetry preload. The controller runs in a separate process. CI saves current and peak RSS, heap usage and the runtime version to a JSON artifact.

## Optional workflow compatibility

Taskflow is an optional compatibility path for explicit `workflow.spec`/`workflow.nodes` requests, pinned to `0.2.10` in `optionalDependencies` (beta Trusted Effects are excluded). A plain prompt-only handoff runs natively in the chosen harness and never resolves or imports Taskflow; `npm install --omit=optional` is supported for those flows. When a workflow is requested, OpenCode lazily imports the pinned host-neutral Taskflow core and Pi lazily resolves the saved-flow extension, and a missing package fails before any model launch with `missing-optional-dependency` and an install hint. Pi materializes a uniquely named saved flow and invokes its deterministic `/tf:<name>` command; `workflow.nodes` is translated into a dependency-preserving FlowSpec, and graph verification happens before model execution. Cursor, Claude, Codex, Gemini, Amp, and generic ACP reject structured workflows before launch.

State reads and commits are serialized per job and commits are checked against the active lease owner. Lock acquisition and atomic snapshot replacement retry transient Windows file-contention errors while preserving the last good snapshot. Recovery, terminal transitions, trace appends, and monotonic event sequencing cannot overwrite one another across MCP processes. Request indexes retain every resume attempt while resolving the newest attempt for recovery.
